# Спецификация: упорядочивание структуры репозитория Larix CDE

## 1. Краткое описание

Необходимо убрать из корня репозитория внутренние Python-файлы, конфигурацию
тестов и служебные сценарии. В корне должны остаться только понятные
пользователю точки входа, описание проекта и Git-конфигурация. Перенос не
должен менять поведение приложения или состав единого переносимого EXE.

## 2. Цели

1. Сделать корень репозитория компактным и понятным для публикации на GitHub.
2. Разнести код приложения, инструменты сборки и конфигурацию по назначению.
3. Переименовать каталог результата сборки `portable` в `release`.
4. Сохранить запуск из исходников тремя пользовательскими BAT-файлами.
5. Сохранить сборку одного автономного `Larix_CDE.exe`.

## 3. Не входит в задачу

- Изменение интерфейса и бизнес-логики Larix, VitroCAD, SIGNAL и ProjectPoint.
- Изменение шаблонов и содержимого `Archive`.
- Изменение набора Python-зависимостей.
- Создание установщика или публикация файлов на GitHub.
- Полная пересборка EXE в рамках этого изменения.

## 4. Целевая структура

```text
CDE/
├─ run.bat
├─ build_single_exe.bat
├─ install_dependencies.bat
├─ README.md
├─ .gitignore
├─ app/
│  ├─ launcher.py
│  ├─ assets/
│  ├─ core/
│  ├─ plugins/
│  └─ shared/
├─ tools/
│  ├─ build_single_exe.py
│  ├─ Larix_CDE.spec
│  ├─ verify_project.py
│  ├─ verify_single_exe.py
│  └─ smoke_portable.py
├─ config/
│  ├─ requirements.txt
│  └─ pytest.ini
├─ tests/
├─ docs/
├─ Archive/
└─ release/                 # создаётся сборкой и не попадает в Git
```

После реализации настоящие `SPEC.md` и `TASKS.md` переносятся в
`docs/repository-layout/`, чтобы они не оставались в корне.

## 5. Функциональные требования

### FR-1. Корневые точки входа

- `run.bat` запускает приложение из `app/launcher.py`.
- `install_dependencies.bat` устанавливает зависимости из
  `config/requirements.txt`.
- `build_single_exe.bat` запускает весь существующий цикл проверки и сборки.
- BAT-файлы должны работать при запуске из проводника и не зависеть от текущей
  рабочей директории.

### FR-2. Код приложения

- `launcher.py`, `assets`, `core`, `plugins` и `shared` располагаются в `app/`.
- Существующие импорты, поиск ресурсов, обнаружение плагинов и внутренние режимы
  запуска продолжают работать.
- `Archive` не является runtime-зависимостью и остаётся отдельным каталогом в
  корне.

### FR-3. Сборка

- Служебные Python-сценарии и PyInstaller spec располагаются в `tools/`.
- Все пути вычисляются от корня проекта, а не от случайной текущей директории.
- Результат сборки — единственный файл `release/Larix_CDE.exe`.
- Временные файлы сборки не появляются среди пользовательских файлов корня.
- Лог сборки хранится внутри `release/` либо другого игнорируемого служебного
  каталога.

### FR-4. Проверки и тесты

- Конфигурация pytest располагается в `config/pytest.ini`.
- Документированная команда тестов работает после чистого клонирования.
- Тесты получают необходимые пути `app/` и `app/plugins/projectpoint` через
  конфигурацию, без ручного изменения окружения.
- Проверки проекта и собранного EXE учитывают новые каталоги `app`, `tools` и
  `release`.

### FR-5. GitHub и документация

- `release/`, временная папка сборки, логи, окружения и кэши игнорируются Git.
- `Archive` продолжает включаться в репозиторий в очищенном виде.
- `README.md` показывает новую структуру и актуальные команды запуска, тестов и
  сборки.
- Ссылки README на документацию остаются рабочими.

## 6. Пользовательские сценарии

### Запуск

1. Пользователь запускает `run.bat` из корня.
2. Сценарий выбирает доступную команду Python.
3. Открывается прежнее главное меню Larix CDE.

При отсутствии Python выводится понятная ошибка и ненулевой код завершения.

### Установка зависимостей

1. Пользователь запускает `install_dependencies.bat`.
2. Устанавливаются зависимости из `config/requirements.txt`.
3. Ошибка Python или pip не скрывается.

### Сборка

1. Пользователь запускает `build_single_exe.bat`.
2. Выполняются проверка проекта, PyInstaller, проверка EXE и smoke-тест.
3. Готовый файл появляется как `release/Larix_CDE.exe`.
4. Для переноса на другой ПК нужен только этот EXE.

## 7. Архитектурные решения

- `app/` становится корнем runtime-кода. Это позволяет сохранить существующие
  короткие импорты `core`, `shared` и модулей плагинов.
- Корневые BAT-файлы остаются тонкими стабильными оболочками над внутренними
  путями.
- `tools/` содержит только инструменты разработки и сборки, которые не нужны
  приложению во время обычного запуска.
- `config/` содержит зависимости и настройки тестового инструментария.
- Название существующего `smoke_portable.py` разрешается сохранить внутри
  `tools/`, если переименование не даёт пользы; пользовательский термин и путь
  результата в документации должны быть `release`.

## 8. Обработка ошибок и восстановление

- Все BAT-файлы возвращают ненулевой код при ошибке.
- Сообщения об отсутствующих Python, PyInstaller, исходниках или EXE содержат
  актуальные пути.
- Неудачная сборка не удаляет исходники и не создаёт файлы в корне.
- Каталог `release` можно безопасно удалить и создать повторно следующей
  сборкой.

## 9. Ограничения и совместимость

- Windows 10/11 x64.
- Сохраняются Python, PySide6 и PyInstaller текущего проекта.
- Сохраняется один автономный EXE и встроенная CAPTCHA SIGNAL.
- Пути с пробелами и кириллицей должны поддерживаться.
- Пользовательские профили и токены не включаются в Git или EXE.

## 10. Критерии приёмки

1. В корне из файлов остаются только `.gitignore`, `README.md`, `run.bat`,
   `install_dependencies.bat` и `build_single_exe.bat`.
2. Runtime-код и ресурсы находятся в `app/`, инструменты — в `tools/`,
   конфигурация — в `config/`.
3. `run.bat` корректно находит новый entry point.
4. Скрипт установки корректно находит новый файл зависимостей.
5. Сборочные и проверочные сценарии используют `release/Larix_CDE.exe`.
6. `py -B -m pytest -q -p no:cacheprovider -c config/pytest.ini` проходит.
7. Проверка структуры проекта проходит с новыми путями.
8. `git diff --check` не сообщает ошибок, а `release/` игнорируется.
9. README соответствует фактической структуре.
10. Полная сборка EXE не запускается без отдельного запроса пользователя.
